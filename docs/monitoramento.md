# Métricas privadas — T14

As duas APIs usam instrumentação HTTP/JVM/pool já fornecida pelo Actuator/Micrometer. GET /monitoramento/metrics exporta apenas uma lista restrita em formato Prometheus: contagem e soma de duração do HTTP de entrada/saída por método e classe de status; memória JVM, CPU/uptime e conexões Hikari ativas/ociosas/pendentes/máximas quando instrumentadas. URI, URL, nome/ID de pessoa, tenant e conteúdo não são labels. Nenhum dado de negócio é consultado para coletar métricas. Saída HTTP depende dos clientes instrumentados pelo Spring; clientes manuais sem observação não entram automaticamente.

Autenticação exclusiva Authorization: Monitoring <segredo>. MONITORAMENTO_TOKEN deve ter 32–128 caracteres ASCII de letras, números, _ ou -. Ausência/configuração inválida mantém coleta fechada (401), sem ativação implícita. Usar segredo distinto em cada API, gerado fora do git e passado somente no ambiente da API/arquivo de credencial do coletor. Não usar chave de integração/JWT. A credencial concede somente ROLE_MONITORAMENTO e somente GET do endpoint exato. Não autentica rotas comerciais. Resposta no-store; comparação em tempo constante para cargas aceitas. Nunca incluir token em URL, imagem ou comando que o imprima.

Na Central, deploy/monitoramento/prometheus.yml prepara coleta dos hosts internos servirea-api:8080 e central-api:8081, de 30 em 30 segundos, com credentials_file e redirects desabilitados. alertas.yml contém API sem coleta, proporção persistente de 5xx e espera no pool. Caddy bloqueia /monitoramento/* e /api/monitoramento/* no acesso público. Coletor deve rodar na rede privada existente, sem porta publicada para internet, montando configuração e dois arquivos de segredo somente leitura. Nada foi iniciado na VPS nem criou segredos reais.

Configuração de autenticação e arquivos segue a [documentação oficial do Prometheus](https://prometheus.io/docs/prometheus/latest/configuration/configuration/). Antes de ativar em staging, validar com promtool da versão escolhida, testar reachability interna/negação pública, credencial ausente/incorreta, rotação e retenção/espaço em disco. HTTP interno assume rede Docker confiável; fora dela usar transporte protegido. Imagem/versão do coletor deve ser selecionada e fixada na implantação, sem usar latest silenciosamente.

Métricas são agregados de processo, reiniciam com a API e não são extrato financeiro. Latência média usa rate(sum)/rate(count); não oferece p95/p99, histogramas, rastreamento distribuído ou painel Grafana pronto. Alertas preparados não significam alertas entregues: o roteamento e a entrega até um receptor HTTP estão testados (`deploy/testes/alertas.test.sh`), mas o envio real por e-mail só se prova em staging com a chave do Resend. T14 amplo permanece parcial: fila, dashboard e operação externa aguardam outra entrega/homologação.

X-Request-Id recebido só é propagado se ASCII seguro de 1–64 caracteres; caso contrário a API gera UUID. MDC limpo ao final. Log lento do Servirea usa padrão de rota resolvido, evitando caminho bruto com tokens de calendário. Testes com HTTP real verificam coleta/instrumentação e ausência de labels sensíveis.

Instrumentação interna limita tags de rota a 256 (a aplicação possui mais de 100 rotas); exportação continua agregada e sem URI. Ao somar rotas, conferir cobertura e avisos de limite em vez de liberar cardinalidade ilimitada.

Instâncias (02/10/2026): `ecossistema_instancias_por_nivel{nivel}` e `ecossistema_instancias_defasadas` vêm do [painel de instâncias](painel-instancias.md). A fila de comunicados do Servirea exporta `ecossistema_fila_envios_total{canal,resultado}` e `ecossistema_fila_reservas_em_curso`; o mesmo endpoint privado e as mesmas regras de credencial se aplicam.

## Alertmanager (T14)

`deploy/monitoramento/alertmanager.yml` agrupa por alerta e API, lembra de 4 em 4 horas (24 h para `info`), manda tudo para a equipe por e-mail pelo SMTP do Resend e silencia 5xx e pool de uma API que já está sem coleta. **Troque os marcadores `COMPLETAR`** (remetente de um domínio verificado e destinatário) e crie `alertmanager_smtp` com a chave de API; sem isso nada é enviado. `docker-compose.monitoramento.yml` sobe Prometheus e Alertmanager em versões fixas, sem porta pública (túnel SSH para ver as telas).

Cada regra de `alertas.yml` tem caso de disparo e de silêncio em `alertas.teste.yml` (`promtool test rules`); o teste falha se um alerta novo ficar sem caso. Ao mudar uma regra, mude o teste. A API de pessoas e de dados não entra nas métricas, e o canal não leva dado pessoal: o e-mail traz só nome do alerta, API e resumo.
